# ККД: контроль качества данных по целям

Backend тестового задания: проверяет цели и ключевые результаты, сохраняет историю прогонов и предоставляет REST API для метрик, проблем и сравнения с предыдущим прогоном.

Стек: **Java 21, Spring Boot 3.5.16, PostgreSQL 17, Liquibase 4.31.1, Maven 3.9.11, JUnit 5**. Maven устанавливается через включённый Wrapper. Версии библиотек управляются Spring Boot BOM; образы Compose и Dockerfile закреплены digest. Spring Boot 3 выбран согласно прямому требованию задания.

## Запуск

Нужен Docker Engine с доступом к daemon и Docker Compose v2 или новее. Локальные Java, Maven и PostgreSQL для этого способа не требуются.

```bash
docker compose up
```

При первом запуске собирается приложение, PostgreSQL проходит healthcheck, Liquibase создаёт схему и исходные данные, а сервис вычисляет два демонстрационных прогона. API: `http://localhost:8080`. Готовность: `http://localhost:8080/actuator/health/readiness`.

Настройки имеют локальные значения по умолчанию. Для изменения порта или реквизитов БД скопируйте `.env.example` в `.env`. `docker compose down` сохраняет данные в named volume; следующий запуск не создаёт повторные прогоны. После изменения исходников используйте `docker compose up --build`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DB_NAME` | `kkd` | Имя БД в Compose |
| `DB_USER` | `kkd` | Пользователь PostgreSQL |
| `DB_PASSWORD` | `kkd_local` | Пароль для локального запуска |
| `APP_PORT` | `8080` | Порт хоста в Compose / порт приложения вне Compose |
| `JDBC_URL` | `jdbc:postgresql://localhost:5432/kkd` | Адрес БД вне Compose; внутри Compose задаётся адрес `db` |
| `DEMO_ENABLED` | `true` | Демо-миграция и вычисление двух прогонов при старте |
| `TZ` | `UTC` | Часовой пояс контейнеров |

`DEMO_ENABLED=false` на новой БД создаёт схему и справочник правил без тестовых целей и прогонов. На существующей БД эта настройка не удаляет данные. Время для правила устаревания берётся из даты снимка, а не системных часов.

## Архитектура

Один сервис и одна БД. `api` проверяет параметры и формирует HTTP-ответы; `application` организует прогоны и чтение результатов; `domain` содержит независимые от Spring/БД правила, формулы и сравнение; `infrastructure` реализует JDBC, миграции и блокировки.

Каждый прогон сохраняет копии подразделений, целей и КР. Снимок и найденные проблемы записываются одной транзакцией `REPEATABLE READ`; состояние прогона хранится отдельно, поэтому ошибка становится видна как `failed`, но частичные результаты не публикуются. PostgreSQL advisory lock сериализует вычисление прогонов. API читает только завершённые снимки, поэтому последующие правки исходных целей не меняют историю.

Новый прогон выполняется внутренним `RunService.execute(id, snapshotDate)`. Дата должна быть позже последнего завершённого прогона. Отдельного HTTP-метода запуска и еженедельного планировщика в заданном объёме нет. Демо использует этот же вычислитель; результаты не подставляются готовыми SQL-вставками.

Контракты и решения подробно описаны в [requirements.md](specs/requirements.md) и [design.md](specs/design.md).

## Правила

Проверяются только `ACTIVE`-цели и их КР.

| Код | Важность | Условие |
| --- | --- | --- |
| `GOAL_NO_OWNER` | critical | Ответственный отсутствует или состоит из пробельных символов |
| `GOAL_NO_KR` | critical | Нет ни одного КР |
| `KR_WEIGHTS_SUM` | major | Есть КР, но сумма их десятичных весов не равна 100 |
| `KR_STALE_PROGRESS` | minor | Дата обновления факта отсутствует или старше 45 дней относительно снимка |

Ровно 45 дней — допустимо. Цель без КР получает только `GOAL_NO_KR`, без дополнительного нарушения весов. Проверки родительской цели и отсутствующего target не выбраны; родительские связи при этом сохраняются.

## Метрики и дельта

Подразделение включает всех своих потомков. Цель учитывается один раз по своему подразделению. Нарушение КР делает некорректной его цель.

- `clean_goals_share`: доля активных целей без проблем; рост означает улучшение.
- `issues_per_100_goals`: число проблем на 100 активных целей; снижение означает улучшение.
- `critical_issues_count`: количество критических проблем; снижение означает улучшение.

Относительные метрики округляются до одного десятичного знака (`HALF_UP`); дельта равна разности отображаемых значений. При отсутствии активных целей относительные метрики равны `null`, абсолютные счётчики — нулю. При равенстве значений trend — `unchanged`.

Проблема совпадает между прогонами по `(rule_code, object_type, object_id)`. Разность множеств даёт новые и исчезнувшие проблемы, пересечение — сохраняющиеся. Текст и подробности проблемы в ключ не входят. Для каждой стороны используются её собственные снимки подразделений: перенос цели может выглядеть как исчезновение проблемы в старом подразделении и появление в новом.

У первого прогона `compared_to`, прошлые значения, дельты, trend и счётчики `new/persisting/resolved` равны `null`. «Исправленная» означает отсутствие проблемы в текущей области сравнения, в том числе после деактивации или переноса цели.

## API

| Метод | Параметры | Результат |
| --- | --- | --- |
| `GET /api/runs` | Нет | `items`: статус, дата, предыдущий прогон, количество проблем; новые прогоны первыми |
| `GET /api/kkd/summary` | Обязательные `run_id`, `unit_id` | Метрики, важность, дельта; включает дочерние подразделения |
| `GET /api/kkd/issues` | Обязательный `run_id`; необязательные `unit_id`, `rule_code`, `severity`, `limit`, `offset` | `items`, `limit`, `offset`, `total` |

`limit`: 1–100, по умолчанию 20. `offset`: 0–2147483647, по умолчанию 0. Фильтры соединяются через AND. `total` — число всех совпадений до пагинации; за концом списка возвращается пустой `items`. Порядок стабилен: важность, правило, тип объекта, ID объекта. В списке только проблемы выбранного прогона; исчезнувшие отражаются в summary.

Идентификаторы: 1–64 символа из `[A-Za-z0-9_-]`. Неизвестный прогон/подразделение → 404; отсутствующие, повторные, неизвестные, пустые или некорректные параметры → 422. Чтение результатов незавершённого прогона → 422. Ошибки имеют единый формат:

```json
{"error":{"code":"RUN_NOT_FOUND","message":"Run RUN-999 was not found"}}
```

Примеры полных JSON-ответов находятся в [design.md](specs/design.md#5-rest-contract).

## Демонстрационные данные

24 активные цели, по 8 непосредственно в каждом из трёх подразделений: `HQ → UNIT-A → UNIT-B`. Даты прогонов — 19 и 26 октября 2026 года. В каждом есть нарушения всех четырёх правил.

| Показатель HQ | RUN-001 | RUN-002 |
| --- | --- | --- |
| Проблемы | 6 | 7 |
| Доля корректных целей | 75.0% | 70.8% |
| Проблем на 100 целей | 25.0 | 29.2 |
| critical / major / minor | 3 / 2 / 1 | 3 / 1 / 3 |

У RUN-002: **3 новые, 4 сохраняющиеся, 2 исчезнувшие** проблемы.

## Ручная проверка через Postman или curl

Запустите сервис через `docker compose up`. Примеры ниже рассчитаны на стандартные демоданные (`DEMO_ENABLED=true`) и порт 8080. Если порт изменён, замените его в URL.

В Postman создайте HTTP-запрос, выберите **GET**, вставьте URL из соответствующей команды и нажмите **Send**. Авторизация — **No Auth**, тело запроса не требуется. Для браузерного Postman выберите запущенный **Desktop Agent**, чтобы обращаться к `localhost`. Параметры можно редактировать во вкладке **Params**.

Команды curl выполняют те же запросы. Ключ `-i` показывает HTTP-статус и заголовки вместе с JSON-ответом.

### 1. Список прогонов

```bash
curl -i 'http://localhost:8080/api/runs'
```

Ожидается **200**. В `items` сначала `RUN-002` с `issues_count: 7`, затем `RUN-001` с `issues_count: 6`. Оба имеют статус `completed`; второй прогон сравнивается с первым.

### 2. Метрики и сравнение прогонов

```bash
curl -i 'http://localhost:8080/api/kkd/summary?run_id=RUN-002&unit_id=HQ'
```

Ожидается **200**, `compared_to.id: RUN-001` и следующие значения:

| Метрика | value | previous | delta | trend |
| --- | --- | --- | --- | --- |
| `clean_goals_share` | 70.8 | 75.0 | -4.2 | worse |
| `issues_per_100_goals` | 29.2 | 25.0 | 4.2 | worse |
| `critical_issues_count` | 3 | 3 | 0 | unchanged |

В `issues_by_severity` текущие значения: critical — 3, major — 1, minor — 3. В `delta`: `new: 3`, `persisting: 4`, `resolved: 2`.

### 3. Первый прогон без сравнения

```bash
curl -i 'http://localhost:8080/api/kkd/summary?run_id=RUN-001&unit_id=HQ'
```

Ожидается **200**. `compared_to` равен `null`; у метрик `previous`, `delta`, `trend` равны `null`. Счётчики `delta.new`, `delta.persisting`, `delta.resolved` также равны `null`, а не нулю. Текущая доля корректных целей — 75.0.

### 4. Все проблемы и комбинированные фильтры

```bash
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002'
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&unit_id=HQ&rule_code=KR_STALE_PROGRESS&severity=minor'
```

Оба ответа — **200**. Первый содержит `total: 7` и семь проблем. Второй — `total: 3` и проблемы КР `K06`, `K08`, `K09`; все имеют правило `KR_STALE_PROGRESS` и важность `minor`.

### 5. Подразделения

```bash
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&unit_id=UNIT-A'
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&unit_id=UNIT-B'
```

Оба ответа — **200**. Для `UNIT-A` ожидается `total: 1` (проблема `K09`), для `UNIT-B` — `total: 0`, `items: []`. Фильтр включает потомков; в стандартном демо у `UNIT-B` проблем нет, а отдельный интеграционный тест проверяет нарушение в самом глубоком подразделении.

### 6. Пагинация

```bash
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&rule_code=KR_STALE_PROGRESS&limit=1&offset=1'
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&offset=999'
```

Оба ответа — **200**. Первый возвращает только `K08`, при этом `total: 3`, `limit: 1`, `offset: 1`. Второй возвращает `items: []`, но `total: 7`: общее количество не зависит от размера страницы.

### 7. Неизвестные объекты

```bash
curl -i 'http://localhost:8080/api/kkd/summary?run_id=UNKNOWN&unit_id=HQ'
curl -i 'http://localhost:8080/api/kkd/summary?run_id=RUN-002&unit_id=UNKNOWN'
```

Ожидается **404** с `error.code: RUN_NOT_FOUND` для первого запроса и `error.code: UNIT_NOT_FOUND` для второго.

### 8. Некорректные параметры

```bash
# Нет обязательного unit_id
curl -i 'http://localhost:8080/api/kkd/summary?run_id=RUN-002'
# Недопустимый размер страницы
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&limit=0'
# Отрицательное смещение
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&offset=-1'
# Неизвестная важность
curl -i 'http://localhost:8080/api/kkd/issues?run_id=RUN-002&severity=invalid'
```

Каждый запрос возвращает **422** с `error.code: INVALID_PARAMETER` и пояснением в `error.message`.

Эти запросы проверяют HTTP API и не изменяют данные. Для проверки миграций с откатом используйте автоматический Docker-сценарий ниже.

## Тестирование через Docker

Для проверок нужны Docker Engine, Docker Compose и Bash. Java, Maven, PostgreSQL и Python запускаются внутри контейнеров.

Полный автоматический сценарий:

```bash
./scripts/check-all.sh
```

Сценарий создаёт отдельный временный Compose-проект и последовательно выполняет:

1. 30 unit/API-тестов: правила на граничных данных, метрики, дельта, иерархия, валидация параметров и формат ошибок.
2. 9 интеграционных тестов на PostgreSQL 17: снимки и транзакционность, фильтры, пагинация, повторная инициализация, перенос целей и новые подразделения.
3. Запуск приложения и HTTP-проверку демонстрационных прогонов, метрик и дельты.
4. Накат → откат до тега `baseline` → проверку отсутствия прикладных таблиц → повторный накат.
5. Повторную HTTP-проверку после восстановления данных и после рестарта приложения.

При ошибке сценарий завершается с ненулевым кодом. Временные контейнеры и данные удаляются при завершении; основной проект и его БД не затрагиваются. Порты тестового проекта на хост не публикуются.

Только проверка миграций и рестарта:

```bash
./scripts/check-migrations.sh
```

Этот сценарий также автоматически проверяет результаты API до отката, после повторного наката и после рестарта. Откат выполняется Liquibase, а не заменой БД пустым volume.

Обычный `docker compose up` при сборке выполняет unit/API-тесты. Полный набор, включая интеграционные тесты и откат миграций, запускается через `check-all.sh`.
